| Stage | Run 1 | Run 2 |

**`native_probe` and `docling` are fully proven at full scale** — both runs
processed all 286 pages successfully, consistently, in the 6-7 minute
range. This is **substantially faster** than the naive linear extrapolation
from the I1.6 50-page benchmark (`239.2s/50 pages -> ~1367s/286 pages`) —
plausible explanation: the I1.6 sample was deliberately stratified toward
visually-complex pages (40% electrical_diagram/screenshot_ui), while the
real corpus average is more text-heavy and processes faster per page. This
itself is useful data for System Analyst's ongoing threshold/throughput
calibration (not a contradiction of I1.6, a refinement of it — a
non-stratified full-document number).

Earlier (separate, smaller) proof: a full 3-page extract completed the
**entire** pipeline successfully end-to-end (native_probe → docling →
cascade_trigger → paddle_cascade → canonical_store → kg_candidate →
chunking → embedding) against the same real infrastructure —
`OrchestratorResult(document_id=2, pages_stored=3, elements_stored=6,

the remaining gap is a **throughput/robustness** issue at full-corpus
cascade volume, not a correctness issue in the pipeline logic itself.

## 2. Two real bugs found and fixed during this run (both already committed)

1. **`PADDLE_OCR_VL_TIMEOUT_SECONDS` default (60s) too short.** Real
   single-image PaddleOCR-VL inference regularly takes 30-90s+. Raised
   default to 180s (`app/core/config.py`).
2. **No retry on transient timeout.** Added `PADDLE_OCR_VL_MAX_RETRIES`
   (default 2) to `RemoteAPIPaddleOCRVLClient._post` — verified via unit
   test that a request failing once then succeeding is transparently
   recovered. This measurably helped (Run 2 made more progress than Run 1:
   21.7 min vs 12.8 min before failing) but did not fully solve it — see §3.

## 3. Remaining issue — root cause understood, fix not yet implemented

Both runs eventually hit a `describe_figure`/similar request that timed out
on **all 3 attempts** (180s × 3 = up to 9 minutes for that one element)
before the orchestrator gave up and marked the stage `failed`. Two
contributing factors, both diagnosed with reasonable confidence from
observed behavior (not fully instrumented/confirmed on the service side —
flagged honestly as the limit of what was verified):

1. **Some individual images are genuinely slow to process**, consistently
   (not a one-off cold-start — the same request failed 3/3 times within one
   `_post` call). Plausible causes: a large/complex electrical schematic
   generating a long markdown description (VLM token generation time scales
   with output length), or cumulative slowdown after many sequential
   requests (thermal, memory fragmentation — not confirmed).
2. **`paddleocr-vl-service`'s FastAPI route handlers are `async def` but
   call fully synchronous, blocking pipeline code directly** (`app/main.py`
   `describe_figure`/`reparse_table`/`ocr_page`). This blocks Python's
   single-threaded asyncio event loop for the **entire duration** of one
   inference call — confirmed by observing that `GET /health` (which does
   no GPU work at all) also hung for 120+ seconds while a slow inference
   request was in flight. This means requests cannot be served concurrently
   even for trivial endpoints, and likely compounds any genuine per-image
   slowness into apparent "stuck" behavior from the caller's perspective.

**Recommended fix** (not implemented in this session — concrete, scoped
follow-up): change `paddleocr-vl-service/app/main.py`'s route handlers from
`async def` to plain `def` — FastAPI automatically dispatches synchronous
route handlers to a thread pool, which would let `/health` (and, more
importantly, the idle-unload watcher's ability to observe state) stay
responsive during a slow inference call, and is a well-understood, low-risk
change. This does not by itself fix "some images take a very long time" —
that likely needs either a longer timeout+fewer-but-longer retries, or
(more robust) an async job-submission pattern (`POST` returns immediately
with a job id, caller polls) instead of a single long-blocking HTTP call —
a larger design change, appropriately left to System Analyst/PM to weigh in
on given the effort involved, not decided unilaterally here.
