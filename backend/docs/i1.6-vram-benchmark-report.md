# I1.6 — VRAM / Threshold / Throughput Benchmark Report

> Input to System Analyst's SA1.1 (update `Documentation/system-design/02-ingestion-pipeline.md`
> §3-4 with final numbers). This report presents raw data + Backend
> Engineer's proposed reading of it — **the final threshold/strategy
> decision belongs to SA1.1**, not this document.

## TL;DR

- **Docling GPU vs CPU** (§2): GPU is only **~1.4x faster** than CPU on this
  RTX 3060 Laptop (239s vs 335s for 50 pages) — much lower than the design
  doc's indicative 3x-10x estimate. Docling peak VRAM: **~2GB** (2131 MiB),
  drops to 723 MiB after `unload()`.
- **THRESHOLD_TABLE=0.75**: never triggers on this sample (observed table
  confidence floor is 0.90) — recommend SA1.1 consider raising toward
  ~0.90-0.92, **with the caveat that this sample is biased toward
  easy-to-detect tables** (§3.1).
- **THRESHOLD_TEXT=0.6**: untestable from this corpus (no scanned pages
  exist in any of the 7 manuals) — remains a reasonable, unverified safety
  net.
- **Important new finding (§6)**: Docling (PyTorch) and PaddleOCR-VL's local
  backend (PyTorch **+** PaddlePaddle) have a **real pip-environment ABI
  conflict** (`nvidia-nccl-cu12` version clash breaks `import torch`
  entirely) when both frameworks are installed in the same venv — this is a
  **packaging problem, not just a VRAM problem**, and the current
  `backend-worker-gpu` design (one image running both stages) does not yet
  account for it. **No real GPU VRAM number for PaddleOCR-VL local backend
  was obtained** as a result — flagged as a concrete architectural follow-up
  for SA/PM, not silently dropped. See DIRECT MESSAGE in the accompanying
  STATUS REPORT.

## 1. Methodology

### 1.1 Sample selection (50 pages, 10 per category)

Selected via `scripts/i1_6_sample_pages.py` (native PyMuPDF heuristics, no
GPU needed) from all 7 `source-documents/` PDFs, spread across documents (a
per-document cap of 3 pages per category was enforced to avoid clustering).
Manifest: `docs/i1.6-sample-manifest.json`. Categories, exactly 10/10/10/10/10
achieved:

| Category | Heuristic |
|---|---|
| `text_normal` | Stage 1 `text_normal` flag only (no vector_diagram/raster_image/low_text_confidence) |
| `table` | `page.find_tables()` (PyMuPDF native table detector) finds >= 1 table, `vector_diagram` flag absent |
| `electrical_diagram` | Stage 1 `vector_diagram` flag AND `vector_drawing_count >= 300` |
| `screenshot_ui` | Stage 1 `raster_image` flag (embedded raster image) |
| `troubleshooting` | Page text matches troubleshooting keywords (troubleshooting/malfunction/error code/check code/symptom/abnormal) co-occurring with a procedure-shaped keyword (cause/remedy/countermeasure/corrective action), AND page number >= 50 (excludes front-matter/safety-notice false positives — see §5 limitations) |

The 50 selected pages were concatenated (in category order, each page
watermarked with its source document + original page number) into
`docs/i1.6-sample-50pages.pdf` — this is the actual input to Stage 2/4
below, not the full 2.581-page corpus.

### 1.2 Execution environment

Run via **WSL2** (`CLAUDE.md` §5 — Docker/GPU work must never run from
Windows-native shell), but as a **WSL-native `uv` project**
(`~/vrf-chat-bench/backend/`, a minimal copy of `app/`+`scripts/`+
`pyproject.toml`+`uv.lock`), **not** the full `backend-worker-gpu` Docker
image — see §6 for why, and what remains to be verified in the actual
container.

- GPU: NVIDIA GeForce RTX 3060 Laptop, 6144 MiB, confirmed via `nvidia-smi`
  from WSL2 and via `torch.cuda.get_device_name(0)` inside the WSL `uv`
  venv.
- `uv sync --frozen --no-dev` inside WSL resolved `torch==2.13.0+cu130`
  (CUDA-enabled) automatically from the **same universal `uv.lock`** used
  for Windows dev (which resolves `torch==2.13.0+cpu` there) — confirms the
  Dockerfile finding from I1.4 (no special CUDA base image needed, see
  `backend/Dockerfile` worker-gpu stage comment).
- NVIDIA Container Toolkit GPU passthrough into a plain Docker container was
  separately verified working (`docker run --rm --gpus all
  nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi` correctly reports the RTX
  3060 from inside WSL Docker) — supports but does not replace full
  container verification (§6).
- VRAM sampling: background thread polling `nvidia-smi --query-gpu=memory.used`
  every 200ms for the duration of each stage, reporting peak observed value
  (captures full process footprint: CUDA context + allocator + fragmentation,
  not just a framework's internal allocator stats).

## 2. Stage 2 (Docling) — GPU vs CPU, 50-page sample

| Metric | GPU | CPU |
|---|---:|---:|
| Wall-clock | **239.2s** | **335.2s** |
| Speedup | **1.40x** (GPU vs CPU) | — |
| Elements extracted | 606 | 606 (identical — same deterministic parse) |
| Table elements | 27 | 27 |
| Peak VRAM used (absolute) | 2131 MiB | n/a |
| Peak VRAM used (delta over ~100 MiB idle baseline) | **2031 MiB** | n/a |
| VRAM after `unload()` | 723 MiB (down from 2131 MiB peak) | n/a |

**Finding vs design doc estimate**: `02-ingestion-pipeline.md` §4 cited an
**indicative, unverified** 3x-10x GPU speedup range for Docling. The
**actual measured speedup on this RTX 3060 Laptop GPU is only ~1.4x**,
substantially lower than the indicative range. Plausible contributing
factors (not further isolated in this benchmark — flagged for SA1.1/future
investigation, not conclusively diagnosed here):
- RTX 3060 **Laptop** variant (lower TDP/clocks than desktop RTX 3060, which
  the 3x-10x range was likely based on for comparable model classes).
- WSL2/WDDM passthrough overhead (`02-ingestion-pipeline.md` §4 already
  flags this as real but unquantified).
- Docling's layout model (RT-DETRv2-based, per the live run's stack trace)
  processing single pages sequentially (batch=1 effectively, since Docling's
  own internal batching wasn't tuned here) — GPU underutilized relative to
  a batched-inference scenario.
- CPU on the benchmark machine is reasonably capable (16 logical cores in
  WSL2).

**Recommendation for SA1.1**: given only ~1.4x speedup and Docling's low
absolute VRAM footprint (~2GB peak, well within the 6GB budget even
alongside PaddleOCR-VL's estimated need IF they had to coexist — though
they still must not, per the sequential design), it may be worth
re-evaluating whether `DOCLING_DEVICE=cuda` is actually worth the VRAM
budget usage in dev vs simply defaulting to CPU and reserving the full 6GB
headroom for PaddleOCR-VL — this is a **recommendation for discussion**, not
a change made unilaterally (the design doc's `DOCLING_DEVICE=cuda` default
decision came from an explicit Jalal instruction, see
`02-ingestion-pipeline.md` §4 "[KOREKSI 2026-08-09]" — revisiting it is
SA1.1/Jalal's call).

VRAM unload verification: peak 2131 MiB -> 723 MiB after `DoclingParser.unload()`
+ 1s settle time — a real, substantial reduction (confirms `unload()` does
free the bulk of Docling's allocated VRAM), but **not** back down to the
~100 MiB idle baseline. The residual ~620 MiB above idle baseline is
consistent with expected CUDA context/driver-level caching that
`torch.cuda.empty_cache()` does not (and is not designed to) release —
worth Stage 4 accounting for this residual as part of its own budget
headroom, not assuming a full return to 100 MiB baseline between stages.

## 3. Threshold calibration data (raw — SA1.1 decides final values)

### 3.1 `THRESHOLD_TABLE` (design doc starting point: 0.75)

27 table elements across the 50-page sample, all from Docling's own
`table_score` (`ConfidenceReport`, per `app/ingestion/docling_parser.py`):

- Range: **0.9014 - 0.9681**
- Mean: **0.9462**
- **All 27 are above the current `THRESHOLD_TABLE=0.75`** — zero
  `table_reparse` cascade tasks fired for this sample (see §4).

**Important sampling caveat**: the `table` category was selected via
PyMuPDF's own `find_tables()` detector (§1.1) — this likely biases the
sample toward tables that are already easy to detect/parse structurally
(clean grid lines, simple headers), since a table PyMuPDF's simpler
heuristic detector can find is plausibly also one Docling's TableFormer
handles well. Genuinely hard tables (merged multi-row headers, borderless
tables, tables spanning irregular layouts) that `find_tables()` itself
might miss are **under-represented** in this specific 27-table subsample.
This is a real methodological limitation, not just a caveat — it means "0
tables triggered THRESHOLD_TABLE=0.75" should NOT be read as "Docling never
struggles with tables in this corpus," only as "Docling handles
easily-detected tables well."

**Recommendation for SA1.1**: given the observed confidence floor is 0.90
(not near 0.75), consider raising `THRESHOLD_TABLE` toward **~0.90-0.92**
so the trigger has a realistic chance of firing on this corpus's harder
tables (which this sample likely under-represents) — leaving it at 0.75
risks the `table_reparse` cascade path never firing in practice, silently
defeating its purpose. This should ideally be paired with a **follow-up,
deliberately-adversarial table sample** (hand-picked complex spec/error-code
tables with merged headers) before finalizing, rather than relying solely on
this `find_tables()`-biased sample.

### 3.2 `THRESHOLD_TEXT` (design doc starting point: 0.6)

`parse_score` across all 50 pages: **uniformly 1.0** (every single page).
Zero `full_page_ocr` cascade tasks fired (see §4). Confirms the design
doc §1 finding that these are digital-native PDFs, not scans — Docling's
native text-layer parsing succeeds perfectly on every sampled page,
including the 3 pages Stage 1 native probe flagged `low_text_confidence`
(Stage 1's heuristic and Docling's actual `parse_score` disagree on those 3
pages — see §5).

**Recommendation for SA1.1**: `THRESHOLD_TEXT=0.6` cannot be meaningfully
calibrated from this corpus alone, since no page in the 7 source documents
is actually scanned — the trigger is purely a "just in case a scanned page
sneaks in" safety net (per design doc §3's own framing), and 0.6 remains a
reasonable, untested-because-untriggerable safety margin. No change
recommended without a genuinely scanned test page (none available in
`source-documents/`).

## 5. Stage 1 native probe vs Stage 2 Docling disagreement (informational)

3 pages were flagged `low_text_confidence` by Stage 1 (heuristic:
`NATIVE_PROBE_TEXT_DENSITY_MIN=0.0005`/`NATIVE_PROBE_MIN_TEXT_CHARS=40`),
but all 3 had Docling `parse_score == 1.0`. Inspecting the manifest, these
are front-matter/cover-style pages (e.g. a title page with large text but
low character *density* relative to page area, or a mostly-diagram page
with minimal text) — Stage 1's density-based heuristic is intentionally
conservative/cheap (§ design, `app/ingestion/native_probe.py`) and is not
expected to perfectly agree with Docling's own, more expensive text-layer
analysis. This is expected/by-design (Stage 1 exists to be a fast filter
*before* Docling runs, not a final judgment), noted here for completeness,
not flagged as a defect. `NATIVE_PROBE_TEXT_DENSITY_MIN=0.0005` remains
**provisional** per System Analyst's earlier note (validate across all 7
documents, not just Zeggo VRV IV, as part of SA1.1).

## 6. Stage 4 (PaddleOCR-VL, local backend) — attempted VRAM benchmark, **blocked by a genuine environment/packaging conflict** (important finding, not just a caveat)

**No real GPU VRAM peak number for PaddleOCR-VL's local backend was obtained
in this benchmark** — not due to lack of effort/time, but because a real,
reproducible technical blocker was found and is documented in full below.
This is the single most important finding of I1.6 and needs SA/PM attention
(see DIRECT MESSAGE in the accompanying STATUS REPORT) — it affects
`02-ingestion-pipeline.md` §4's architecture assumptions, not just a
threshold number.

### 6.1 What was attempted, in order

1. **`paddleocr` base package** (`uv add paddleocr`) — pipeline construction
   for `PaddleOCRVL(vl_rec_backend="native", ...)` failed immediately:
   `RuntimeError: Engine 'paddle_static' is unavailable because dependency
   'paddlepaddle' is not installed.` The layout-detection submodel
   (`PP-DocLayoutV3`) is a classic PaddlePaddle-format model (`.pdiparams`/
   `.pdmodel`), requiring the actual **PaddlePaddle framework** — a
   completely separate deep learning framework from **PyTorch** (which
   Docling and the VL recognition submodel itself use, per the earlier
   `engine_name: torch` log lines seen in I1.2/I1.4). This was NOT expected
   going into I1.4 — the design doc and I1.4 implementation both implicitly
   assumed PaddleOCR-VL was a single-framework (torch-based) model, since
   the ERNIE4.5-based VL recognition weights are safetensors/`transformers`-
   compatible. **It is not single-framework** — the pipeline mixes both.
2. **`paddleocr[doc-parser]`** (`uv add "paddleocr[doc-parser]"`, backend
   dependency now updated to this, see `pyproject.toml`) — this extra pulls
   `paddlex[genai-client,ocr]`, still does **not** include `paddlepaddle`
   itself (confirmed: `paddlepaddle` absent from `uv pip list` after this
   install). Same `RuntimeError` as above.
3. **CPU-only `paddlepaddle==3.3.1`** (ad-hoc `uv pip install paddlepaddle`
   in the disposable WSL benchmark venv only — **not** added to the real
   `pyproject.toml`/`uv.lock`, see §6.4) — pipeline construction proceeded
   further: the layout submodel gracefully fell back to CPU with a warning
   (`The specified device (GPU) is not available! Switching to CPU
   instead.` — confirms the graceful-degradation path works correctly), and
   the **real PaddleOCR-VL-1.6-0.9B model weights downloaded successfully**
   (1.8GB, cached at `~/.paddlex/official_models/PaddleOCR-VL-1.6/`).
   However, the VL recognition submodel's device changer **hard-fails**
   (does not gracefully degrade) when `PADDLE_OCR_VL_DEVICE=cuda` is
   requested and PaddlePaddle isn't CUDA-compiled: `ValueError: The device
   should not be 'gpu:0', since PaddlePaddle is not compiled with CUDA`.
   This at least confirms `app/ingestion/paddleocr_vl_cascade.py`'s
   orchestration code (`_ensure_loaded`/`_run_predict`/bbox rendering/model
   construction call) is structurally correct up to this point — a real
   integration surface was exercised, not just mocks.
4. **`paddlepaddle-gpu==3.3.1` (CUDA 12.6 build)**, installed to match the
   exact same version as the CPU build (`pip install
   https://paddle-whl.bj.bcebos.com/stable/cu126/paddlepaddle-gpu/paddlepaddle_gpu-3.3.1-cp312-cp312-linux_x86_64.whl`)
   — installed successfully (~4GB download: paddlepaddle-gpu itself 1.9GiB +
   bundled `nvidia-cudnn-cu12`/`nvidia-cublas-cu12`/`nvidia-nccl-cu12`/etc.
   runtime packages), and **verified working in isolation**
   (`paddle.is_compiled_with_cuda() == True`, `paddle.device.set_device('gpu:0')`
   succeeds). **But this broke `import torch` entirely**:
   ```
   ImportError: .../torch/lib/libtorch_cuda.so: undefined symbol: ncclCommResume
   ```

### 6.2 Root cause

`paddlepaddle-gpu` and `torch` both vendor `nvidia-nccl-cu12` (and other
`nvidia-*` CUDA runtime packages) as **separate pip packages installed into
the same shared site-packages namespace**. Installing `paddlepaddle-gpu`
(via an ad-hoc `uv pip install <wheel-url>`, which does not go through the
project's locked dependency resolution) pulled in an `nvidia-nccl-cu12`
version incompatible with the ABI `libtorch_cuda.so` was compiled against —
Docling (which imports `torch` directly, see `app/ingestion/docling_parser.py`)
would fail to import entirely in this state.

### 6.3 Architectural implication — needs SA/PM attention

`backend-worker-gpu` (`01-architecture-overview.md` §6, `Dockerfile`) is
currently **one image/one Python venv** running Docling (Stage 2, PyTorch)
and PaddleOCR-VL local backend (Stage 4, PyTorch **+** PaddlePaddle) **in
the same process/environment**, sequentially. The 6GB VRAM constraint
analysis in `02-ingestion-pipeline.md` §4 (sequential execution + explicit
`unload()` between stages) correctly solves the **VRAM budget** problem, but
does **not** solve this **separate, more fundamental packaging/ABI
compatibility problem** — the two frameworks may not be pip-installable
together in the same environment at all, independent of VRAM, if a mutually
compatible `nvidia-nccl-cu12` (and other shared `nvidia-*` packages) version
doesn't exist for both. This was not identified until this benchmark;
worth flagging explicitly since it means "sequential + unload" alone may
not be sufficient for `PADDLE_OCR_VL_BACKEND=local` to actually work in the
container as currently designed.

**Not resolved in this session** (recommended as explicit follow-up, not
silently dropped) — two candidate directions, for SA/PM to weigh in on:
1. **Process/venv isolation within the same container**: run the local
   PaddleOCR-VL inference in a separate Python venv/subprocess from Docling
   (naturally fits the already-sequential design — a fresh subprocess also
   trivially guarantees zero residual VRAM from Docling, arguably a cleaner
   `unload()` guarantee than same-process `torch.cuda.empty_cache()`).
   Adds real complexity to the Celery task/Dockerfile (two venvs baked into
   `worker-gpu`, or a subprocess call out to a second image).
2. **Favor `remote_api` in practice for the combined worker**: run a
   dedicated, PaddlePaddle-only service/container for PaddleOCR-VL (already
   a documented fallback path in `02-ingestion-pipeline.md` §4 "ambang
   kebijakan fallback ke cloud API" — this finding strengthens the case for
   defaulting to it for `backend-worker-gpu` specifically, reserving `local`
   for a standalone PaddleOCR-VL-only worker/environment that never installs
   `docling`/`torch` from Docling's side at all).

### 6.4 Repo/dependency state — clean, no broken changes committed

To be explicit: `paddlepaddle`/`paddlepaddle-gpu` were **never** added to
the real `pyproject.toml`/`uv.lock` (verified: `grep paddlepaddle
pyproject.toml` returns nothing) — both were ad-hoc `uv pip install`s in the
disposable `~/vrf-chat-bench/` WSL benchmark copy only (§1.2), which is not
part of the repository and was discarded after this benchmark. The real
dependency change from I1.6 is `paddleocr` -> `paddleocr[doc-parser]` (a
legitimate, necessary fix — without it, even the CPU fallback path in §6.1
step 3 could not have been reached at all).

## 7. Sequential VRAM safety (Docling + PaddleOCR-VL never coexisting)

**Confirmed for Docling's own unload (§2)**: peak 2131 MiB -> 723 MiB after
`DoclingParser.unload()` + CUDA cache empty — a real, substantial VRAM
release.

**Not confirmed for the full Docling-then-PaddleOCR-VL sequence** — blocked
by the §6 packaging conflict (never reached a state where both could be
exercised in the same process/environment to observe the handoff). This
remains explicitly unverified, tracked as follow-up alongside §6.3's
resolution (Q1.2's "urutan sekuensial Docling→unload→PaddleOCR-VL
benar-benar terjadi" verification depends on §6.3 being resolved first).

## 8. What this benchmark does NOT verify (explicit scope boundary)

- **The actual `backend-worker-gpu` Docker image was not built/run** for
  this benchmark — a WSL-native `uv` project was used instead (§1.2), which
  gets identical GPU/VRAM numbers (same GPU, same driver, same
  `uv.lock`-resolved dependency versions) faster than a full Docker image
  build+model-download cycle would have allowed within this session. What
  is NOT yet confirmed: that `docker compose --profile gpu build` actually
  succeeds end-to-end and that `torch.cuda.is_available()` is `True` inside
  the *built container* specifically (as opposed to the WSL-native venv
  used here). This is real remaining work, appropriately scoped to Q1.2
  (QA Engineer, "Verifikasi operasional... backend-worker-gpu jalan via
  WSL") per `02-phase-1-ingestion.md`'s own task split, not re-done here.
- **Zero of the 44 available `visual_description` cascade tasks were run to
  completion** against the real PaddleOCR-VL model — blocked by the §6
  environment conflict before any `client.describe_figure()` call could
  succeed. `_first_prediction_to_dict`/`_extract_markdown_text`'s
  best-effort field-name assumptions (`app/ingestion/paddleocr_vl_cascade.py`)
  remain **unverified against a real PaddleOCR-VL `Result` object** — flagged
  as a concrete follow-up item once §6.3 is resolved (verify/correct the
  mapping against real output, not just fakes).
- **`remote_api` backend was not live-tested** (no real endpoint available)
  — unchanged from the I1.4 STATUS REPORT limitation, verified only via
  `httpx.MockTransport` unit tests.
- **PaddleOCR-VL local backend's actual peak VRAM usage is unmeasured** —
  see §6. A rough, explicitly-unverified estimate based on downloaded model
  size alone (1.8GB VL weights + ~130MB layout weights, fp32 as downloaded):
  likely **3-5GB peak** including activation memory at modest image
  resolution; with `PADDLE_OCR_VL_DTYPE=fp16` (wajib in dev) weights would
  roughly halve to ~1GB, plausibly **~2-3GB peak** — but this is an estimate
  only, not a measurement, and should not be used for capacity planning
  without real verification.
